## 3. Why Mendi has been impossible at $0 so far

The Mendi headband (consumer SKU, 2-channel prefrontal NIRS) is locked down by design:

1. **No public BLE characteristics published.** The device speaks BLE only to the official Mendi mobile app. Reverse-engineering the protocol would require packet capture from a rooted Android phone (technically possible, ~10–20 hours of work, falls in the "free but slow" budget bucket).
2. **No CSV/JSON export from the Mendi app.** The phone app shows you a session graph and a score; it does not let you export raw HbO2/HbR per sample. It exports "session summary" PNGs at most.
3. **No public Mendi API.** Mendi has not opened a developer API.

Every approach we tried assumed one of these three constraints would magically resolve. None did.

## 4. What would actually work — three honest paths, ranked

### **Path A — Manual session-summary logging (FREE, ~$0, ~30 sec/session)**

What we already half-built but never operationalized. After each Mendi session on your phone:
- Open the Streamlit "Mendi Neurofeedback Session" tab
- Type the final score, duration, and intention into the form
- Hit save — it writes one row to `mendi_sessions` with the LCC↔score mapping and GILE breakdown

**What this gives us:** session-level time series (1 number/day-or-session). Sufficient for trend analysis, NOT for within-session neurofeedback.

**What it does NOT give us:** real-time HbO2/HbR samples, the actual fNIRS waveform. Can't be used as a Phase B feature in the URB #826 regression.

**Recommendation:** start doing this *today* if you're going to keep using Mendi at all. It's the only zero-effort capture path that produces data we can actually analyze.

### **Path B — Mendi BLE reverse-engineering (FREE-ish, ~10-20 hours of agent time, $0 hardware)**

Capture BLE packets while the Mendi app talks to the headband (using `nRF Connect for Mobile` on your phone — free), decode the characteristics, write a Python BLE client in `bleak`. This is the path the implementation plan from Nov 21 *assumed* would just work; it didn't, because nobody reverse-engineered.

**Honest probability of success:** 50/50. Mendi's firmware may use encrypted BLE pairing or rotating keys. We won't know until the packet capture is done.

**Cost:** ~$0 if I do it; only your time is the captures (~30 min on the phone).

**Recommendation:** queue this as a future URB if Path A's session-summary data turns out to be insufficient. Don't start it today — it's not on the URB #826 critical path.

### **Path C — Switch to a developer-friendly fNIRS device ($300+, NOT FREE)**

Devices like the **OpenBCI Cyton + NIRS add-on** or **Artinis OctaMon** expose raw HbO2/HbR over USB or BLE with documented APIs. Out of budget.

**Recommendation:** off the table for the <$50 budget cycle.

## 5. The asymmetric-standards #69 honest verdict

**Mendi is currently a sunk cost.** Six implementation attempts, ~3,800 lines of code, and one architectural plan have produced no usable data. Continuing to invest in the existing code paths without BLE reverse-engineering will produce more code and zero data.

**The cheapest forward move is Path A** — start manually logging session summaries through the existing UI today. If after 21 sessions the data is too sparse to inform anything, we honestly retire Mendi from the active stack rather than pretend it's contributing.

**Mendi is NOT relevant to URB #826 Phase B / §10.6.** Phase B's regression already has its needed feature set (Oura HRV + PPG biosig + 3 genome features + Polar H10 incoming). Mendi prefrontal HbO2 would be a *separate* line of evidence (a different URB about prefrontal coupling, not biophoton/EM-DNA), so don't let Mendi delay the H10 collection window.
